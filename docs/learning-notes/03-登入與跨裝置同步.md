# 登入與跨裝置同步

## 這段在做什麼（三句話以內）

讓手機和電腦用同一組密碼登入後，打勾紀錄會透過 Cloudflare D1 互相同步，包含「取消打勾」。
沒登入、沒網路時照常在本機使用，連線後自動補同步。
伺服器端改用 Hono，登入、工作階段、同步 API 與 SQL 都有單元測試，在 CI 上跑。

## 關鍵觀念

| 觀念 | 白話說明 | 在哪裡 |
|---|---|---|
| **密碼雜湊（PBKDF2）** | 不存密碼，只存「密碼算了 10 萬次之後的結果」加上隨機的鹽（salt）。登入時用同樣的鹽和次數再算一次，結果相同就是對的。算 10 萬次是故意的：讓暴力猜密碼變慢 | `worker/auth/password.ts` |
| **固定時間比較** | 比較兩個雜湊時，不在第一個不同的位元組就停下來，避免攻擊者從回應快慢推測出雜湊 | `password.ts` 的 `equalBytes` |
| **HttpOnly Cookie** | 登入後瀏覽器收到一個 Cookie，JavaScript 讀不到（HttpOnly）、只走 HTTPS（Secure）、別的網站發的請求不會帶（SameSite=Strict） | `worker/auth/routes.ts` |
| **工作階段只存雜湊** | D1 只存權杖的 SHA-256；就算資料庫外洩，也拿不到能用的 Cookie | `worker/auth/authRepo.ts` |
| **墓碑（tombstone）** | 取消打勾不真的刪除，而是標成「已刪除」。真的刪掉的話，另一台裝置分不出「被刪了」還是「還沒收到」 | `src/progress/progressRepo.ts` |
| **dirty 標記** | 本機每筆紀錄記得自己「還沒送到伺服器」；同步成功、而且送出後沒再改過，才清掉 | `progressRepo.ts` 的 `applySyncResult` |
| **游標（cursor）與 rev** | 伺服器每寫入一筆就給一個遞增編號 `rev`；前端記住上次拿到第幾號，下次只拿更新的 | `worker/sync/syncRepo.ts` |
| **較新者為準（last-writer-wins）** | 兩邊都改了同一筆，保留 `updatedAt` 較晚的。本機修改時間只會往前走，裝置時鐘慢了也不會輸給自己根據的版本 | `src/sync/merge.ts`、`src/progress/logs.ts` 的 `nextUpdatedAt` |
| **upsert** | SQL 的「沒有就新增、有就更新」：`INSERT … ON CONFLICT DO UPDATE … WHERE 送來的較新` | `syncRepo.ts` |
| **防抖（debounce）** | 30 秒內連續打勾，只在最後一次的 30 秒後同步一次，省下請求數 | `src/sync/scheduler.ts` |
| **測試替身** | Node 內建 SQLite 假扮 D1、fake-indexeddb 假扮瀏覽器資料庫、假的 fetch 假扮網路，核心邏輯不用真的連雲端就能測 | `worker/testing/sqliteD1.ts` |

### 範例：一次同步發生什麼事

1. 前端送出 `{ since: 上次的游標, changes: 本機 dirty 的紀錄 }`。
2. 伺服器逐筆 upsert：送來的較新才寫入，並給新的 `rev`。
3. 伺服器回傳 `rev` 大於 `since` 的紀錄（包含其他裝置寫的，也包含自己剛送的）。
4. 前端清掉沒再改過的 dirty、把伺服器紀錄合併進本機、存新游標；有紀錄被改變就重新整理畫面。

## 為什麼這樣設計，放棄了什麼

| 決定 | 放棄的做法 | 理由 |
|---|---|---|
| 不登入也能用 | 打開就要登入 | 離線時要能打勾（離線可用是需求） |
| PBKDF2 | bcrypt、argon2 | Workers 內建 Web Crypto 就有 PBKDF2，不用額外套件 |
| 工作階段存 D1 | JWT | JWT 要多一個簽章機密，而且發出去就無法真正登出 |
| 墓碑 | 真的刪除＋另記刪除清單 | 兩份資料要一起維護，容易不一致 |
| 一支 API 先推後拉 | 推、拉分兩支 API | 少一次請求，也不用處理「推成功、拉失敗」的中間狀態 |
| 用遞增的 rev 當游標 | 用時間戳 | 同一毫秒的兩筆可能漏掉 |
| Node 內建 SQLite 模擬 D1 | Cloudflare 官方測試環境 | 和目前 Vitest 版本相容性未確認；這個做法簡單、CI 不用帳號 |
| 全域鎖定（5 次錯就鎖 15 分鐘） | 依 IP 鎖定 | 單一使用者沒有好處 |

**實作時遇到的事：**

- Worker 的型別（Cloudflare 的 `RequestInit`）沒有 `credentials` 欄位；兩台裝置的整合測試要同時用到前端和 Worker 程式，所以在前端程式裡用型別斷言處理，並寫註解說明。
- 同步重新讀取時，如果剛好有一次打勾寫入，讀到的會是舊資料；所以讀取期間有寫入就再讀一次。
- 產生雜湊的指令稿用管線送入兩行時，第一次讀取把兩行都吃掉了；改成共用一個逐行讀取器。

## 面試可能被問的問題與回答方向

| 問題 | 回答方向 |
|---|---|
| 密碼怎麼存？ | 只存 PBKDF2 雜湊（鹽＋10 萬次），比較用固定時間；機密放 Worker secret，不進版本庫 |
| 為什麼用 Cookie 不用 localStorage 存權杖？ | HttpOnly 讓 JavaScript 讀不到，被注入腳本也偷不走；SameSite=Strict 擋跨站請求 |
| 離線時改的資料怎麼同步？ | 本機先寫、標 dirty；恢復連線、切到背景、打勾 30 秒後批次送出 |
| 兩台裝置改同一筆怎麼辦？ | 較新者為準；本機修改時間只往前走；單一使用者衝突機率很低，這是刻意選擇的簡單做法 |
| 刪除怎麼同步？ | 墓碑：標記刪除而不是真的刪，讓刪除也成為一筆可以同步的修改 |
| 怎麼測後端？ | SQL 和 API 用 Node 內建 SQLite 模擬 D1，`app.request` 直接打 Hono；兩台裝置的情境也寫成整合測試 |
| 怎麼防暴力破解？ | PBKDF2 讓每次嘗試變慢；15 分鐘內錯 5 次就鎖 |
